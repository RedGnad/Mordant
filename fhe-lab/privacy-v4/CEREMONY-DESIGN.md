# M-PRIV5A design note: dealerless 2-of-3 ceremony

Written before implementation. It maps every required protocol round to the exact Lattigo
6.2.0 type and method, and records the assumptions that the implementation must not silently
change.

## Root cause being removed

`NewRuntime` (`threshold.go:64`) calls `generateThresholdParties`, which builds all three
`rlwe.SecretKey` values and all three `multiparty.ShamirSecretShare` values inside one process.
`ProvisionThresholdOperators` (`distributed_threshold.go:108`) then serialises each
`party.tsk` into an operator bundle. In `cmd/privacy-coordinator` that process is also the
evaluator, and it evaluates the circuit at line 141, before it provisions at line 146 and
before `DetachThresholdParties` at line 172. The evaluator therefore holds complete
decryption capability while it holds both client ciphertexts.

The README states the property this mission depends on: *"S can be generated
non-interactively and without a trusted dealer by having each party generating a random
degree-(t-1) polynomial S_i with S_i(0) = s_i, and by implicitly take S = sum S_i."*

## Two regimes, one ideal key

Lattigo's t-out-of-N scheme is an extension of the N-out-of-N scheme. Both address the same
ideal secret key:

```
s = S(0) = sum_i s_i          where s_i is operator i's locally sampled RLWE secret
S(alpha_i) = sum_j S_j(alpha_i)   is operator i's retained Shamir share
```

This gives two usable regimes, and the design uses each where it is correct:

| Phase | Participants | Secret used in `GenShare` | Why |
|---|---|---|---|
| Setup (CPK, RLK, GAL) | all N = 3 | raw local `s_i` | N-out-of-N regime; aggregate of 3 shares targets `sum s_i = S(0)` |
| Release (key switch) | any t = 2 | `Combiner.GenAdditiveShare` output `S(alpha_i)*l_i` | t-out-of-N regime; the 2 combined shares also sum to `S(0)` |

Both regimes produce keys and shares for the same `s`, so a key generated by all three
operators is releasable by any two. This is what lets every operator participate in key
generation (a mission requirement) while keeping 2-of-3 liveness for release.

`Combiner.GenAdditiveShare` reads `activesPoints[:threshold]` and excludes only `ownPoint`
from the Lagrange product. The active set passed at release time must therefore be exactly
the t participating points, and the caller's own point must be inside it. The existing
release path already satisfies this; the ceremony must not widen it.

## Round-to-type mapping

| Round | Actor | Lattigo type and method |
|---|---|---|
| R0 local secret | each operator | `rlwe.NewKeyGenerator(params).GenSecretKeyNew()` |
| R0 identity | each operator | `ed25519.GenerateKey` (ceremony signing key, distinct from FHE material) |
| R1 CRS contribution | each operator | 32 random bytes; CRS seed = H(domain ‖ fingerprint ‖ ceremonyID ‖ epoch ‖ rosterDigest ‖ contributions in point order) |
| R2 polynomial | each operator | `multiparty.Thresholdizer.GenShamirPolynomial(t, sk_i)` |
| R3 private shares | operator i to operator j | `Thresholdizer.GenShamirSecretShare(alpha_j, S_i, &share)`, sent over an authenticated private channel |
| R4 aggregate | each operator | `Thresholdizer.AggregateShares` over the N received shares, giving `S(alpha_i)`; then erase `S_i` and the received shares |
| R5 CPK | all 3 | `PublicKeyGenProtocol.SampleCRP(crs)` / `GenShare(sk_i, crp, &share)` / `AggregateShares` / `GenPublicKey` |
| R6 RLK round 1 | all 3 | `RelinearizationKeyGenProtocol.SampleCRP` / `GenShareRoundOne(sk_i, crp, ephem_i, &share)` / `AggregateShares` |
| R7 RLK round 2 | all 3 | `GenShareRoundTwo(ephem_i, sk_i, combinedOne, &share)` / `AggregateShares` / `GenRelinearizationKey` |
| R8 Galois x9 | all 3 | `GaloisKeyGenProtocol.SampleCRP` / `GenShare(sk_i, galEl, crp, &share)` / `AggregateShares` / `GenGaloisKey` |
| R9 seal | each operator | erase `s_i` and `ephem_i`; persist only `S(alpha_i)` + signing key; sign the key manifest |
| Release | any 2 | `Combiner.GenAdditiveShare` then `multiparty.KeySwitchProtocol` toward zero (unchanged from V3) |

Galois elements are the nine already required by the circuit: steps
`{1, 2, 4, 8, 16, 32, 64, -64, 128}` (`threshold.go:21`). The parameters
(LogN 15, LogQ 12 primes, LogP 3 primes, t = 65537) and the policy circuit are unchanged.

RLK is the only two-round protocol. `GenShareRoundOne` returns an ephemeral secret key that
must survive until round two, so the operator holds one extra secret across R6 and R7 and
must erase it at R9.

## Process topology

```
ceremony-operator 1 ─┐   private pairwise mTLS (Shamir shares)
ceremony-operator 2 ─┼── peer-to-peer, coordinator excluded
ceremony-operator 3 ─┘

        │ public protocol shares only
        ▼
ceremony-coordinator ── aggregates public shares, writes public artifacts, never a secret type
        │
        ▼
collective-public-material.bin · collective-evaluation-keys.bin · key-manifest.json (3 signatures)
        │
        ├─► Client A / Client B: verify manifest, then encrypt
        └─► evaluator: public material only, no secret deserialisation path
```

The ceremony coordinator is a separate process from the evaluator. The mission permits the
evaluator to aggregate public messages, but separating them makes the capability audit a
static property of the evaluator binary rather than a runtime argument.

## CRS: replacing the fixed kill-test seed

The current CRS is `sampling.NewKeyedPRNG([]byte("mordant-lattigo-v6.2.0-kill-test-crs"))`,
a hardcoded constant. V4 replaces it with a per-ceremony collaborative seed: every operator
contributes 32 random bytes, and the seed is the hash of the domain, parameter fingerprint,
ceremony ID, key epoch, roster digest, and all contributions in point order. No single
operator fixes the CRS, and the seed is recomputable by any verifier from public data.

**Classified limitation.** Contributions are revealed in one round, without commit-then-reveal.
Under Lattigo's documented passive-adversary model every operator follows the protocol, so
this is sound. An active adversary revealing last could bias the seed; defending against that
needs commit-reveal, which is only meaningful alongside the correctness proofs that Lattigo
does not implement. This is recorded as a limitation, not fixed here.

## Ceremony binding

Every ceremony message and the final manifest bind: parameter fingerprint, roster digest
(operator IDs, points, signing keys), threshold, ceremony ID, key epoch, CRS commitment,
public-key commitment, relinearization-key commitment, Galois-key commitments, policy-circuit
commitment. A message whose binding does not match the receiving operator's own state is
rejected before any secret material is used.

## Retry and share reuse

Lattigo's SECURITY.md warns that retrying a multiparty protocol with the same shares and
public polynomial can leak secret material, and that the countermeasures are not implemented.
The ceremony is therefore one-shot per ceremony ID and per operator: an operator that has
emitted a share for a round refuses to emit another for the same (ceremonyID, epoch, round,
recipient). A failed ceremony is terminal; recovery means a fresh ceremony ID, fresh local
secrets and a fresh CRS. Restart after a crash resumes only from durably sealed terminal
state, never by re-running a round.

## What this design cannot claim

Passive-adversary security only, per Lattigo. No proof that an operator generated its share
honestly. No proof of correct FHE execution. Roster and PKI distribution remain a lab
bootstrap assumption. Three processes on one host under one administrator is process
separation, not independent organizational custody.
